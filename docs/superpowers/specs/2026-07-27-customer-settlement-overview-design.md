# 客户结算总览与单客户明细设计

## 背景

现有 `/settle/customer/sheet` 以销售出库单、销售退货单为粒度展示，并在同一页面完成对账和结算。该方式不能让用户快速了解每个客户的结算进度，且一个客户会占用多行。

## 目标

将客户结算拆分为总览页和单客户明细页：

- `/settle/customer/sheet` 是客户结算总览，每个客户仅一行。
- 总览显示待对账、待结算、部分结算、已结算四种状态，每种状态均展示单据数和金额。
- 点击客户所在行的“结算”按钮，进入新增的单客户结算明细页。
- 新明细页承接现有工作台的单据筛选、确认对账、确认结算、关联单据跳转和导出能力。

## 页面与路由

### 客户结算总览

保留路由 `/settle/customer/sheet`。筛选条件为客户；保留查询、结算记录和导出操作。移除单据号、业务类型筛选、勾选列、确认对账及确认结算按钮。

表格字段如下：

| 字段组 | 列 |
| --- | --- |
| 基础信息 | 客户、客户编号 |
| 待对账 | 单据数、金额 |
| 待结算 | 单据数、金额 |
| 部分结算 | 单据数、金额 |
| 已结算 | 单据数、金额 |
| 操作 | 结算 |

金额按源单据金额聚合，销售退货金额保留负数方向。页脚按当前页数据汇总所有金额列和单据数列。

### 单客户结算明细

新增路由 `/settle/customer/sheet-detail`，必须携带 `customerId`。页面固定展示该客户的销售出库、销售退货单据；保留现有明细页的状态、单据号、业务类型等筛选及直接对账、直接结算能力。

总览页点击“结算”时通过 `customerId` 打开该路由。路由参数缺失或客户无权访问时，页面给出明确错误提示，不允许在明细页切换到其他客户。

## 后端接口与数据流

新增客户结算总览查询和导出接口，权限分别沿用 `customer-settle:sheet:query` 与 `customer-settle:sheet:export`。

服务层分别批量查询满足现有数据权限的销售出库单与销售退货单，过滤已被交易占用的单据，然后在内存中按客户和结算状态聚合。聚合完成后统一排序、分页并返回。此方案避免按客户逐条查询数据库；因为两个源单据分属不同表，且项目禁止直接编写 SQL，不引入跨表 SQL 聚合。

总览响应的每个客户行至少包含：客户 ID、客户编号、客户名称，以及每个结算状态的 `count` 和 `amount`。状态口径为：待对账、待结算、部分结算、已结算；其他状态不计入四项统计。

现有 `sale-settle-infos` 接口保留给单客户明细页使用。明细页请求中强制注入路由的 `customerId`，后端继续以现有数据权限校验源单据；直接对账、直接结算提交仍由既有服务执行。

## 错误处理

- Controller 负责请求校验、日志和 `InvokeResult` 包装。
- Service 负责批量查询、聚合及业务校验；业务错误使用 `DefaultClientException`。
- 对账、结算时继续基于源单状态和版本做并发校验，状态变化须提示用户刷新后重试。

## 测试

- Java 单元测试：两类源单据的四状态聚合、同客户合并、不同客户隔离、销售退货负数金额、空结果与分页。
- 前端 Vitest：总览行统计展示、结算按钮构造新路由参数、单客户明细页强制使用路由客户 ID。
- 回归测试：单客户明细页确认对账、确认结算及退货负数结算仍保持现有行为。

## 非目标

- 不改变客户对账、结算的金额分摊规则。
- 不改变客户结算记录页面。
- 不引入逐客户数据库查询或直接 SQL。
