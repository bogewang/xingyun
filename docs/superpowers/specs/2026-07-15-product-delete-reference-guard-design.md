# 商品删除单据引用保护设计

## 背景与目标

商品删除为逻辑删除，会将 `base_data_product.available` 更新为 `false`。为保持采购和销售单据历史数据可追溯，只要商品已被任一采购或销售单据明细引用，就禁止删除。

## 范围

校验以下四类明细：

- 采购订单明细；
- 采购收货单明细；
- 销售订单明细；
- 销售出库单明细。

任一类型存在该商品的引用即禁止删除，不按单据状态过滤。库存、零售、盘点及其他业务不在本次范围内。

## 架构设计

`xingyun-basedata` 不依赖 `xingyun-sc`，而 `xingyun-sc` 已依赖 `xingyun-basedata`。为避免形成循环依赖，在 `xingyun-core` 定义商品删除前引用检查接口；由 `xingyun-sc` 提供实现。

删除调用链如下：

1. `ProductServiceImpl.deleteById` 在更新商品可用状态前调用核心接口；
2. 仓储模块实现使用 MyBatis-Plus 查询四张明细表的 `product_id`；
3. 检测到任一引用时抛出 `DefaultClientException("商品已被采购或销售单据引用，不能删除！")`；
4. 无引用时继续原有逻辑删除和数据变更事件发布。

接口只承担“商品是否允许删除”的跨模块约束，不返回业务实体。核心模块不依赖具体单据实现。

## 错误处理与事务

删除方法保留 Service 层 `@Transactional`。引用校验发生在状态更新之前；抛出业务异常时事务回滚，商品不会被置为不可用，也不会发布删除事件。

## 测试

新增单元测试覆盖：

- 四类单据各自存在引用时，删除均抛出业务异常且不更新商品状态；
- 四类单据均无引用时，商品可按原逻辑删除；
- 引用检查实现对任一明细表命中均返回禁止删除结果。
